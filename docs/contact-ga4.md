# 質問・相談フォームとGA4 運用手順書

対象：https://ai-shachosan.com/ ／ 作成：2026-11-21

## 1. 仕組みの概要

| 役割 | 使うもの | 追加費用 |
| --- | --- | --- |
| 受付の保存（受付の成立点） | 既存のCloudflare D1（`meo_inquiries` テーブル。EmDashのテーブルとは別） | なし（既存D1の無料枠内の想定） |
| 運営者への通知 | Cloudflare Email Routing の `send_email`（宛先・差出人はサーバー側で固定） | なし |
| 迷惑送信対策 | Cloudflare Turnstile（サーバー側で検証）＋ D1で数える回数制限 | なし |
| 通知の再試行 | 既存の毎分のcronで、未通知の受付を再送（最大6回、間隔を伸ばす） | なし |
| 受付の確認・削除 | `/inquiries`（EmDashに管理者でログインしたときだけ表示） | なし |
| アクセス解析 | GA4（閲覧者が許可した場合だけ読み込む） | なし |

- **受付成功の条件**：入力検証 → 回数制限 → Turnstile検証 → D1への保存が成功した時点。通知メールが失敗しても受付は成功のまま、`/inquiries` に「通知失敗」と表示され、cronが再送します。
- **フォームを出す条件**：Turnstileの鍵と通知メールの設定がそろったときだけ。そろっていない間は `/contact` に「フォームは準備中です」とメールアドレスを表示し、APIも受け付けません（503）。
- **GA4を動かす条件**：`GA4_MEASUREMENT_ID` が設定され、ホスト名が `ai-shachosan.com`、EmDashに未ログイン、閲覧者が「許可する」を選んだとき。プレビューURL、ローカル、`/_emdash/`、`/inquiries` では動きません。

## 2. 本番で必要な設定（運営者の作業）

秘密の値はチャットやコミットに貼らず、Cloudflareのダッシュボードに直接入力してください。

### 2-1. Turnstile（迷惑送信対策）

1. Cloudflareダッシュボード →「Turnstile」→「ウィジェットを追加」。
2. ウィジェット名：`ai-shachosan contact`、ホスト名：`ai-shachosan.com`、ウィジェットモード：「マネージド」。
3. 表示された **サイトキー**（公開値）を、`wrangler.jsonc` の `TURNSTILE_SITE_KEY` に入れる（Claudeに渡せば反映します）。
4. **シークレットキー**は、Workers & Pages →「ai-shachosan」→「設定」→「変数とシークレット」→「追加」で、種類「シークレット」、名前 `TURNSTILE_SECRET_KEY` として保存。
5. 同じ場所に、名前 `INQUIRY_HASH_SALT`、値は長いランダムな文字列（パスワード生成機能などで作った32文字以上）をシークレットとして保存。回数制限のためにIPアドレスを変換するときに使います。

### 2-2. 通知メール（Email Routing）

1. ダッシュボード →「ai-shachosan.com」→「メール」→「Email Routing」を有効にする。
   - MXレコードなどが追加されます。**ai-shachosan.com で既に別のメールを受信している場合は、有効化する前に確認してください**（現在のDNSに既存のMXがあれば、そちらが影響を受けます）。
2. 「宛先アドレス」に `taiwa.kawamura@gmail.com` を追加し、届いた確認メールのリンクを押す（「確認済み」になること）。
3. `wrangler.jsonc` の `"send_email"` 行のコメントを外す（Claudeに依頼可）。差出人は `form@ai-shachosan.com`（`INQUIRY_FROM`）です。受信用のアドレスを作る必要はありません。
4. 最初の通知がGmailの迷惑メールに入っていないか確認し、入っていたら「迷惑メールではない」にします。

### 2-3. GA4

| 設定 | 値・操作 |
| --- | --- |
| プロパティ | このサイト用のプロパティ（なければ作成）。レポートのタイムゾーン：日本、通貨：円 |
| ウェブストリーム | URL `https://ai-shachosan.com`。表示された測定ID（`G-` から始まる）を `wrangler.jsonc` の `GA4_MEASUREMENT_ID` に入れる |
| 拡張計測機能 | ストリームの歯車から：**ページビューの「ブラウザの履歴イベントに基づくページの変更」をOFF**、スクロール数・離脱クリック・サイト内検索・フォームの操作・動画エンゲージメント・ファイルのダウンロードをすべてOFF（このサイトでは page_view を手動で1回だけ送るため） |
| データ保持 | 管理 → データの収集と修正 → データ保持 → イベントデータ・ユーザーデータとも **14か月**（プライバシーポリシーの記載と合わせる） |
| Googleシグナル・広告 | 有効にしない（管理 → データの収集：Googleシグナルはオフのまま。Google広告とのリンクもしない） |
| キーイベント | 管理 → イベント →「キーイベントを作成」→ 名前 `generate_lead`。**question_submit はキーイベントにしない** |
| カスタムディメンション | 管理 → カスタム定義 →「カスタムディメンションを作成」、範囲「イベント」で次の4つ（ディメンション名＝イベントパラメータ名でOK）：`inquiry_type`、`placement`、`source_article`、`page_type` |
| 内部トラフィック | 管理 → データストリーム → タグ設定を行う → 内部トラフィックの定義 で自分のIPを登録 → 管理 → データフィルタ の「Internal Traffic」を **まず「テスト」のまま** 数日確認し、自分のアクセスだけが対象になっていることを確かめてから「有効」にする。なお、EmDashにログインしている間はタグ自体が動きません |

### 2-4. Search Console

登録済み（ドメインプロパティ・サイトマップ送信済み）。主要記事の「URL検査」でインデックス状況を確認する程度で大丈夫です。Search Consoleの数字（検索結果での表示・クリック）とGA4の数字（ページ表示・セッション）は定義が違うので、足したり比べて差を問題にしたりしないでください。

## 3. 本番反映の手順

1. このPRをマージ（この時点では設定が空なので、フォームは「準備中」、GA4は動きません。表示の変更だけが反映されます）。
2. 2-1・2-2を行い、サイトキーと `send_email` の反映をClaudeに依頼 → マージ。
3. 運営者が自分で `/contact` からテスト送信（本文に「テスト」と書く）→ Gmailに通知が届く／`/inquiries` に表示される／「削除」で消せる、を確認。
4. 2-3を行い、測定IDの反映をClaudeに依頼 → マージ。
5. GA4の「管理 → DebugView」またはTag Assistantで、許可後に `page_view` が1回、記事末の入口で `contact_click`、入力で `contact_form_start`、送信成功で `question_submit` / `generate_lead` が届くことを確認（通常のレポートへの反映は24〜48時間かかります）。
6. ヘッダーのメニュー名「メールで相談」を「質問・相談」に変更（EmDash管理画面 → メニュー → primary。Claudeに依頼可）。

## 4. 問題が出たときに戻す方法

| 戻したいもの | 方法 |
| --- | --- |
| フォームだけ止める | `wrangler.jsonc` の `TURNSTILE_SITE_KEY` を空にしてデプロイ → `/contact` は「準備中」＋メールアドレスの表示に戻る（記事・計測には影響なし） |
| 通知メールだけ止める | `send_email` 行をコメントに戻す → フォームも自動で「準備中」になる（受付だけ続けたい場合は `INQUIRY_REQUIRE_NOTIFY` を `"false"` にして `/inquiries` で確認） |
| GA4だけ止める | `GA4_MEASUREMENT_ID` を空にしてデプロイ → タグ・同意表示・「アクセス解析の設定」が消える |
| すべて元に戻す | GitHubでこのPRの「Revert」→ マージ。D1の `meo_inquiries` テーブルは残るので、受付内容は失われません |

## 5. UTMの運用（SNSからのリンク）

### 命名ルール

| パラメータ | 値 |
| --- | --- |
| `utm_source` | `x` / `threads` / `instagram` / `note` / `substack`（表記を変えない） |
| `utm_medium` | SNS投稿は `social`、noteなどの記事からの紹介は `referral`、定期メールは `email` |
| `utm_campaign` | 企画単位。例：`launch_202611` |
| `utm_content` | 投稿単位。例：`checklist_post_01` |

例：
`https://ai-shachosan.com/posts/first-checklist?utm_source=x&utm_medium=social&utm_campaign=launch_202611&utm_content=checklist_post_01`

- 英小文字・数字・アンダースコアだけを使う。氏名・メール・薬局名・読者のIDは入れない。
- サイト内のリンクには付けない。

### 新しい企画・投稿コードを追加する

1. GitHubで `src/config/utm.ts` を開き、鉛筆アイコンで編集。
2. `campaigns` か `contents` の配列に `"新しいコード",` を1行追加して保存（コミット）→ マージ。
3. デプロイ後に、そのコードを付けたリンクを投稿する。

登録していない値は、そのパラメータだけ採用されません（他の登録済みの値と、通常の参照元の判定は残ります）。

## 6. GA4で見るレポートと探索の作り方

### A. 流入元ごとの比較
レポート → 集客 → **トラフィック獲得**。ディメンション「セッションの参照元/メディア」。指標に「セッション」「キーイベント（generate_lead）」を表示し、`question_submit` は「イベント数」で別に見る（右上の鉛筆 → 指標を追加 → イベント数、フィルタでイベント名＝question_submit）。初回の接点を見たいときだけ「ユーザー獲得（最初のユーザーの参照元/メディア）」を使い、両方を混ぜない。

### B. 入口の記事の比較
レポート → エンゲージメント → **ランディングページ**。セッションとキーイベントを比較。「最初に入った記事」と「相談する直前の記事」は別の数字です。

### C. 記事の次に見たページ
探索 →「経路データ探索」→ 始点「ページタイトルとスクリーン名」で主要記事を選ぶ → 次のステップを展開（記事→支援ページ、記事→別記事、記事→質問・相談 など）。

### D. 相談ページの前に見たページ
探索 →「経路データ探索」→ 右上「最初からやり直す」→ **終点**に「質問・相談」（ページタイトル）を設定 → 前のステップを展開。比較する期間をメモしておく。

### E. フォームの進み方
探索 →「ファネルデータ探索」→ ステップを編集：
- 全体：①ページタイトル＝「質問・相談」 ②イベント名＝contact_form_start ③イベント名＝question_submit **または** generate_lead
- 相談だけ：①contact_form_start かつ inquiry_type＝consultation ②generate_lead
- 記事質問だけ：①contact_form_start かつ inquiry_type＝question ②question_submit

支援ページを必須ステップにしない（記事から直接相談する人を「離脱」にしないため）。用件別のユーザー数を足して全体の人数にしない。

作った探索は、左上の名前を「A 流入元」などに変えて保存すると、次から一覧で開けます。

### 週に1回見ること
1. どの流入元・入口記事から訪問があったか（A・B）
2. どの記事から質問・相談ページへ進んだか（D）
3. 質問と相談をそれぞれ何件受け付けたか（`/inquiries` の件数が正。GA4は傾向）
4. 入力開始後に受付まで進まない割合が増えていないか（E）
5. 実際に届いた相談の課題・希望（`/inquiries`）

### 数字の読み方の注意
- GA4の数字は、許可した閲覧者の分だけです。拒否・ブロック・端末の違いで欠けるため、受付件数は `/inquiries` と完全には一致しません。
- page_view は表示された回数で、読了や理解を表しません。メール作成・コピーは送信完了ではありません。
- 経路やファネルの数字だけで「この記事が相談を増やした」と断定しないでください。

## 7. 受付一覧（/inquiries）

- EmDashに管理者でログインした状態で https://ai-shachosan.com/inquiries を開く。
- 「通知失敗」「通知未設定」の受付は「通知を再試行」で再送できます。
- 対応が済んで不要になった受付は「削除」してください（元に戻せません）。保存期間の目安を決めたら、プライバシーポリシーにも反映します。

## 8. 設定値の一覧

| 名前 | 種類 | 場所 | 内容 |
| --- | --- | --- | --- |
| `GA4_MEASUREMENT_ID` | 公開 | wrangler.jsonc | `G-…` |
| `ANALYTICS_HOSTS` | 公開 | wrangler.jsonc | `ai-shachosan.com` |
| `TURNSTILE_SITE_KEY` | 公開 | wrangler.jsonc | Turnstileのサイトキー |
| `TURNSTILE_SECRET_KEY` | **秘密** | ダッシュボードのシークレット | Turnstileのシークレットキー |
| `INQUIRY_HASH_SALT` | **秘密** | ダッシュボードのシークレット | ランダムな長い文字列 |
| `SITE_HOSTS` | 公開 | wrangler.jsonc | Turnstileで受け付けるホスト名 |
| `INQUIRY_TO` / `INQUIRY_FROM` | 公開 | wrangler.jsonc | 通知の宛先／差出人 |
| `INQUIRY_LIMIT_*` | 公開 | wrangler.jsonc | 回数制限（送信元ごと1時間5件、全体1時間30件・1日100件） |
| `send_email`（`INQUIRY_MAIL`） | バインディング | wrangler.jsonc | Email Routing設定後にコメントを外す |

`wrangler.jsonc` の `vars` はデプロイのたびに上書きされるため、公開値はダッシュボードではなく `wrangler.jsonc` で管理します（シークレットは上書きされません）。

ローカル確認用：`.dev.vars` に `INQUIRY_DEV_MODE=mock` を書くと、開発サーバーでだけTurnstileと通知がモックになります（本番では無効）。
